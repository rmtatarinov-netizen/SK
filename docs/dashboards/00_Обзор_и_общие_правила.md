# ТЗ дашбордов SK-системы. 00. Обзор и общие правила

Документ задаёт сквозные правила для пяти управленческих дашбордов системы учёта
предписаний строительного контроля Генподрядчика (OCR → LLM → SQLite → Telegram).
Все формулы привязаны к фактической схеме БД (`prescriptions_system/src/db/models.py`)
и отчётному слою (`src/reports/queries.py`). Значения в примерах — демонстрационные,
помечены «пример».

Комплект документов:

| № | Документ | Дашборд | Маршрут |
|---|---|---|---|
| 00 | Настоящий файл | Общие правила | — |
| 01 | [Панель руководителя проекта](01_Панель_руководителя.md) | Главный экран руководства | `/dash/executive` |
| 02 | [Исполнительская дисциплина и сроки](02_Дисциплина_и_сроки.md) | Сроки, просрочки, воронка | `/dash/discipline` |
| 03 | [Критичность, качество и риск](03_Критичность_и_риски.md) | Категория А, повторные, риск-балл | `/dash/risk` |
| 04 | [Проблемные виды работ и дефекты](04_Виды_работ_и_дефекты.md) | Виды работ, кластеры причин | `/dash/works` |

## 1. Навигация и связь экранов

```
Реестр предписаний (/prescriptions)  ←— единый drill-down для всех дашбордов
        │
        ├── /dash/executive      (сводка «что горит», вход на штаб)
        ├── /dash/discipline     (сроки и исполнительская дисциплина)
        ├── /dash/risk           (критичность А/В/С, повторные, риск-балл)
        ├── /dash/works          (аналитика по видам работ и дефектам)
        └── /dash/contractors    (рейтинг подрядчиков и ответственных)
                  │
                  └── карточка подрядчика / объекта / предписания
```

Общий цикл работы руководителя: агрегированный показатель → клик → реестр с
готовым фильтром → карточка предписания → действие (назначить, напомнить,
эскалировать) → фиксация в `prescription_history`.

## 2. Глобальная панель фильтров (единна для всех экранов)

Фильтры хранятся в URL (query string) — состояние восстанавливается по ссылке
и сохраняется при drill-down/back. Состав и соответствие полям БД:

| Фильтр | Поле БД | Тип | Примечание |
|---|---|---|---|
| Период | `prescriptions.doc_date` (дата выдачи) | диапазон / пресеты week/month/year/custom | Скользящее окно уже реализовано в `generator.get_period_dates` (срез — вторник текущей недели) |
| Объект | `prescriptions.object_id` → `objects.name` | список, мульти | — |
| Участок / корпус / захватка | `prescriptions.section_id` — **отсутствует**, см. §8 | дерево | Зависит от выбранного объекта |
| Подрядчик / субподрядчик | `prescriptions.contractor_id` → `contractors.name` | поиск + мульти | — |
| Управление строительством | `prescriptions.mgmt_id` → справочник «управления строительства» (таблица `construction_management`) | список | — |
| Ответственный | `prescriptions.responsible_user_id` → `users.full_name` | поиск + мульти | Включая значение «не назначен» (`IS NULL`) |
| Категория А/В/С | `prescriptions.category_id` → `prescription_categories.name` | чипы | Справочник настраиваемый |
| Вид предписания | `prescriptions.kind_id` → `prescription_kinds.name` | список | Уже есть в БД |
| Вид работ | `prescriptions.work_type_id` — **отсутствует**, см. §8 | список + ручной ввод (гибридный справочник) | Отдельный от «вида предписания» |
| Статус | `prescriptions.status` | чипы | См. §3 |

Сквозной параметр качества данных: «включить неподтверждённые» — записи с
`requires_review = 1` (не проверены инспектором после OCR/LLM). По умолчанию
в управленческих срезах **исключаются**, в реестре отображаются с меткой «черновик».

## 3. Статусы: фактические и производные

Фактический enum `PrescriptionStatus`: `draft_for_signature, new, under_review,
in_work, fixed_pending_review, closed, rejected`. Соответствие бизнес-названиям:

| Название в дашбордах | Статус БД | Условие |
|---|---|---|
| Черновик | `draft_for_signature` | В аналитику не входит |
| Новое | `new` | — |
| Назначено | `under_review` + назначен `responsible_user_id` | Рассмотрение/распределение |
| В работе | `in_work` | — |
| Ожидает подтверждения (проверки) | `fixed_pending_review` | Подрядчик заявил об устранении |
| Устранено | `fixed_pending_review`/`closed` при заполненном `actual_fix_date` | Производная отметка |
| Закрыто | `closed` | Проверено и принято инспектором |
| **Просрочено** | производный: `status IN (new, under_review, in_work, fixed_pending_review) AND deadline < today` | Отдельного статуса в БД нет — считается на лету (совпадает с `queries.overdue_count`) |
| Аннулировано | `rejected` | — |

Открытое предписание (`OPEN_STATUSES` из `queries.py`): `new, under_review,
in_work, fixed_pending_review`. Все KPI «открытые» считают именно это множество.

## 4. Базовые определения (обязательны во всех дашбордах)

| Термин | Формула |
|---|---|
| Дней в работе (возраст) | `today − COALESCE(issue_date, doc_date)` для открытых |
| Срок устранения, дн. | `actual_fix_date − COALESCE(issue_date, doc_date)` для закрытых; если `actual_fix_date IS NULL` — `DATE(closed_at) − doc_date` |
| «В срок» | `actual_fix_date <= deadline`; при `actual_fix_date IS NULL` и закрытом статусе — `DATE(closed_at) <= deadline` |
| Просрочено | открытое И `deadline < today` |
| Дней просрочки | открытое: `today − deadline`; закрытое с нарушением: `COALESCE(actual_fix_date, DATE(closed_at)) − deadline` |
| Без ответственного | открытое И `responsible_user_id IS NULL` |
| Без срока | открытое И `deadline IS NULL` |
| Доля устранения в срок, % | устранённые в срок / все устранённые (закрытые) за период × 100 |
| Фотофиксация есть | `EXISTS(attachment WHERE kind='photo' AND prescription_id=…)` |
| Подтверждённая нормативная ссылка | `EXISTS(prescription_norm_refs WHERE status='confirmed')` |

Дата «сегодня» — дата сервера на момент рендера; в каждом дашборде выводится
подпись «данные на {дата, время}» (механизм `generated_at` уже есть).

## 5. Единая палитра и цветовые правила

Деловой стиль: белый фон `#FFFFFF`, светло-серые панели `#F4F6F8`,
тёмно-синий интерфейс `#1F3A5F` (шапка, заголовки, оси графиков), текст `#1A1A1A`.

| Семантика | Цвет | HEX | Применение |
|---|---|---|---|
| Критический риск / просрочено / категория А | красный | `#C0392B` | KPI, точки, столбцы, счётчики |
| Предупреждение / 1–7 дней до срока / категория В | оранжево-жёлтый | `#E67E22` / `#F1C40F` | ранние предупреждения |
| В норме / устранено и подтверждено | зелёный | `#27AE60` | закрытия, «в срок» |
| Нет данных / не назначен / черновик | серый | `#9E9E9E` | дыры в данных, требующие действий |
| Информационный | тёмно-синий | `#1F3A5F` | «все», «открытые», базовые ряды |

Правила:

1. Красный и оранжевый применяются **только** к показателям с порогами из
   документов 01–05; не украшать интерфейс.
2. Любой красный показатель кликабелен и **требует детализации** — переход
   в реестр с фильтром, давшим это число (правило №7 §6).
3. Цвет не является единственным носителем смысла: дублируется подписью,
   иконкой или знаком ▲/▼ (доступность, ч/б печать).
4. Диапазон одного графика — не более 3 акцентных цветов + оттенки серого.

## 6. Сквозные правила drill-down и UX

1. Клик по KPI-карточке → `/prescriptions?<параметры фильтра, порождающие метрику>`.
   Соответствие карточка→фильтр задано таблицей drill-down в каждом документе.
2. Клик по элементу графика (столбец объекта, пузырь подрядчика, ячейка
   тепловой карты) → реестр или детальная аналитика объекта/подрядчика.
3. Клик по строке таблицы → карточка предписания `/prescriptions/{id}`.
4. Каждый график имеет выпадающее меню «Показать: график | таблицу» и кнопку
   «Выгрузить» (CSV/XLSX — механизм `/reports/export.*` расширяется параметрами фильтра).
5. Хлебные крошки: Дашборд → Срез → Реестр. Кнопка «Назад к дашборду» сохраняет
   фильтр и прокрутку.
6. Все переходы передают полный набор активных фильтров §2.
7. Формула карточки KPI выводится во встроенной подсказке (иконка ⓘ):
   название, точная формула, период, исключение черновиков `requires_review`.
8. Пустое значение ≠ 0: при отсутствии данных карточка показывает «—» серым и
   подсказку «нет данных за период».

## 7. Требуемые возможности интерфейса (действий из дашбордов)

Реализуются один раз, используются всеми дашбордами (через quick-меню строки
или модальное окно карточки):

| Действие | Куда пишется | Уведомление |
|---|---|---|
| Назначить ответственного | `responsible_user_id`, `prescription_history` | событие `responsible_changed` |
| Изменить срок **с обязательной причиной** | `deadline`, history + `overdue_reason` (см. §8) | `deadline_changed` |
| Направить напоминание | ручная постановка в очередь `notifications` | `deadline_approaching` / `deadline_overdue` (Telegram/MAX — `recipient_channels`) |
| Запросить отчёт об устранении | история + шаблон уведомления | уведомление подрядчику |
| Назначить повторную проверку | `status → fixed_pending_review/under_review`, комментарий инспектора | `status_changed_*` |
| Открыть карточку | — | — |
| Выгрузка Excel/PDF/XLSX | `/reports/export.*` с текущими фильтрами | — |
| Зафиксировать решение руководителя | `prescription_history.comment` (role manager) | — |

Валидация: сменить срок без причины — запрещено (форма не отправляется);
назначение ответственного — только активным пользователям роли
`contractor_responsible` или внутреннего ИТР.

## 8. Дефицит данных: миграции и новые справочники (единый перечень)

В текущей БД **отсутствуют** поля, требуемые ТЗ. Вводятся алгоритом Alembic
(каталог `migrations/versions`), справочники — гибридные: пополняются вручную
через `/admin/directories` и при вводе предписания (паттерн уже реализован для
`prescription_kinds`).

| # | Объект | Определение | Используется в |
|---|---|---|---|
| M1 | Таблица `sections` (id, name, object_id FK, parent_id FK — дерево участок/корпус/захватка, is_active) | Участок строительства | все дашборды |
| M2 | `prescriptions.section_id` FK → sections, индекс | Разрез участка | все |
| M3 | Таблица `work_types` (id, name unique, is_active) + `prescriptions.work_type_id` FK | Вид работ (отдельно от «вида предписания» `kind_id`) | 01, 03, 04, 05 |
| M4 | Таблица `overdue_reason_types` (id, name) + `prescriptions.overdue_reason_type_id` FK, `overdue_reason_text` Text | Причина просрочки по предписанию | 02 |
| M5 | `prescriptions.recurrence_of_id` FK (self) / `is_repeat` bool | Повторное замечание (выявлено повторно после закрытия ранее) | 02, 03, 04, 05 |
| M6 | Таблицы `defect_clusters` (id, work_type_id, title, centroid_ref, is_manual) и `defect_cluster_members` (cluster_id, prescription_id, distance, confirmed_by_user_id) | Группы повторяющихся причин (эмбеддинги `justification`+`description`; эмбеддинги уже есть — `norm_chunk_embeddings`, ChromaDB) | 04 |
| M7 | Таблица `prescription_comments` (id, prescription_id, user_id, text, created_at) | Сквозные комментарии (сейчас только в history) | 02 |
| M8 | `system_config` ключ `dash.risk_weights` (JSON) | Настраиваемые веса приоритета/индексов (см. 03 §4, 04 §5, 05 §4) | 01, 03, 04, 05 |
| M9 | `users.management_id` FK → справочник управлений | Прикрепление ответственного к управлению (для разрезов «управление × дисциплина») | 02, 05 |
| M10 | Индексы: `ix_prescriptions_object_deadline(object_id, deadline)`, `ix_prescriptions_contractor_status(contractor_id, status)`, `ix_prescriptions_worktype(work_type_id)` | Производительность срезов | все |
| M11 | `contractors.parent_contractor_id` FK (self), `contract_no` | Иерархия подрядчик → субподрядчик, номер договора | 05 |

Правило: дашборды не показывают метрики полей M1–M7 до применения миграций;
в макетах такие блоки помечены «после доработки схемы» (не «0»!).

## 9. Права доступа

Основа — `UserRole` (admin, inspector, contractor_responsible, manager) и
`require_role` (как в `reports.py`: `CAN_VIEW = admin|inspector|manager`).

| Роль | Дашборды 01–05 | Область данных | drill-down |
|---|---|---|---|
| manager (руководство), admin | все | вся организация | полный реестр |
| inspector | все | все объекты / закреплённые | полный реестр + действия инспектора |
| contractor_responsible | только 02 и карточки | **только** предписания, где `responsible_user_id = user` или `contractor_id = user.contractor_id` | реестр в своей области |

Данные LLM (извлечённые поля, предложенные нормоссылки `NormRefStatus.SUGGESTED`,
предложенные кластеры M6) — только с пометкой «предложено, не подтверждено»;
подтверждает инспектор (`confirmed_by_user_id`, `confirmed_at`).

## 10. Демонстрационные данные

Все значения в макетах помечены «пример» и синтетичны. Реальные показатели в
ТЗ не приводятся, так как фактическая статистика на момент написания отсутствует.
Числа в примерах согласованы между карточками одного экрана (KPI = сумма
детализации) — это требование и к приемке (§11).

## 11. Общие критерии приемки (дополняются в каждом документе)

1. Каждый KPI сходится с drill-down: реестр по клику содержит ровно N записей.
2. Главный экран умещается на 1920×1080 без вертикальной прокрутки.
3. Фильтры §2 применяются ко всем блокам одновременно (< 2 с на полном реестре
   до 50 000 записей, SQLite с WAL).
4. Красный/оранжевый пороги соответствуют таблицам цветов из документов 01–05.
5. Черновики `requires_review=1` по умолчанию исключены из KPI; переключатель работает.
6. Экспорт по текущему срезу (CSV/XLSX) повторяет видимые колонки таблиц.
7. Отсутствие поля из §8 не отображается как «0» или пустой график.
8. Все подписи, единицы («шт.», «дн.», «%»), дата отсечки видны на экране.
