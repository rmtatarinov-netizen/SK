# 01. Панель руководителя проекта

Назначение: за 30–60 секунд показать текущее состояние качества и
исполнительской дисциплины по объектам, выделить критические риски, просрочки,
проблемные участки и ответственных лиц. Один главный экран под монитор
1920×1080 (руководитель не прокручивает и не ищет — всё видно сразу).

Аудитория: генеральный директор, директор по строительству, главный инженер,
руководитель проекта, руководитель службы строительного контроля (роль
`manager`/`admin`, права — 00 §9).

Сквозные правила (фильтры, статусы, палитра, drill-down, миграции) — в
[00_Обзор_и_общие_правила.md](00_Обзор_и_общие_правила.md). Все числа ниже —
**пример**.

> **Статус: реализовано (срез 2026-10).** Маршруты `/dash/executive` и
> `/dash/executive/data`; миграция `a7c31f9d2b54` (M1–M4, M5, M8, M10);
> метрики `src/dashboards/metrics.py`; тесты `tests/test_executive_dashboard.py`
> (включая проверку сходимости KPI↔drill-down). Блок «последнее действие»
> в топ-10 и LLM-саммари — следующей итерацией.

## 2. KPI-карточки (ряд 1)

| # | Карточка | Формула (по 00 §3–4) | Drill-down (`/prescriptions?…`) | Цвет |
|---|---|---|---|---|
| K1 | Открытые предписания | COUNT(status ∈ OPEN_STATUSES) | `status=open` | серый/синий базовый |
| K2 | Критические открытые, категория А | K1 ∧ `category_id → prescription_categories.name='А'` | `status=open&category=А` | **красный всегда** |
| K3 | Просроченные | открытые ∧ `deadline < today` | `status=open&overdue=1` | красный, если > 0 |
| K4 | Дедлайн в ближайшие 7 дней | открытые ∧ `today ≤ deadline ≤ today+7` | `status=open&due_within=7` | оранжевый |
| K5 | Устранено за период | `DATE(closed_at) BETWEEN период` (или `actual_fix_date`) | `status=closed&period=…` | зелёный |
| K6 | Доля устранения в срок, % | устранённые в срок / устранённые за период × 100 | список нарушивших срок за период | ≥80 зелёный; 60–79 жёлтый; <60 красный |
| K7 | Средний срок устранения, дн | AVG(`actual_fix_date − doc_date`) по устранённым за период | те же записи, сортировка по сроку | синий + спарклайн тренда |
| K8 | Δ открытых к предыдущему периоду, % | (K1_тек − K1_пред) / K1_пред × 100 | реестр «выдано в текущем» vs «выдано в пред.» | ▲ рост — красный, ▼ снижение — зелёный |

Под каждой карточкой: единица, период, ⓘ с формулой. Карточки K1–K4 считаются
**на текущий момент** (срез сегодня), K5–K7 — за выбранный период; это указано
на самой карточке («на сегодня» / «за период»).

## 4. Блок «Топ-10 самых опасных открытых предписаний» — колонки

| Колонка | Источник |
|---|---|
| Номер | `doc_number` (+ метка типа: предписание заказчика `customer` / внутреннее `internal`) |
| Объект | `objects.name` |
| Участок | `sections.name` (M1–M2) |
| Вид работ | `work_types.name` (M3) |
| Категория | `prescription_categories.name` (А — красный чип) |
| Дата выдачи | `COALESCE(issue_date, doc_date)` |
| Срок устранения | `deadline`; пусто → «не задан» (серый чип, см. приоритет §6) |
| Дней просрочки | расчёт по 00 §4; 0/пусто → «—» |
| Ответственный | `users.full_name`; NULL → «не назначен» (серый чип) |
| Подрядчик | `contractors.name` |
| Краткое содержание | `description` первых 80 симв. (LLM-саммари — см. 03 §6), hover → полный текст |
| Последнее действие | `prescription_history`: дата + тип последнего события (назначен, изменён срок, напоминание, комментарий) |
| Открыть карточку | ссылка `/prescriptions/{id}` |

Доп. колонка справа (служебная): риск-балл (0–100) и полоска-градация фона
строки (красный → оранжевый → жёлтый). Дефолтная сортировка — по баллу.

## 5. Блок «Требуют решения руководителя»

Автоматический список (3–5 позиций, не больше — иначе теряется смысл).
Правила попадания:

1. Категория А просрочена более 14 дней.
2. Категория А без ответственного или без срока (данные не полны →
   решение именно руководителя о назначении).
3. Предписание без движения (нет событий в `prescription_history`) более
   10 дней при открытой категории А/В.
4. Повторное замечание (M5) по уже закрытой ранее теме на том же участке.
5. Объект, где доля просроченных А за период > 30%.

Формат строки: `⚠ {объект} — {что нужно решить} — {кого ответственнить} —
{балл}` + кнопка действия (эскалация/назначение) из 00 §7.

## 6. Алгоритм приоритизации (порядок сортировки B6 и B3)

Итоговый приоритет = сумма весов (шкала и настройка — 03 §4, общие веса
хранятся в `system_config.dash.risk_weights`, M8):

| Фактор | Условие | Балл (пример шкалы) |
|---|---|---|
| Категория | А / В / С | 50 / 25 / 10 |
| Просрочка | > 14 дн / 1–14 дн | 30 / 20 |
| Приближение дедлайна | ≤ 3 дн / ≤ 7 дн | 15 / 8 |
| Повторность (M5) | повторное после закрытия | 20 |
| Нет ответственного | открытое, `responsible_user_id IS NULL` | 15 |
| Нет плана/срока устранения | открытое, `deadline IS NULL` | 15 |
| Нет подтверждённой нормоссылки | нет `norm_refs(status='confirmed')` при обязательности | 10 |

Правила: максимальный вес всегда у категории А; просрочка и близость дедлайна
складываются с категорией; ties-break — больший срок просрочки, затем
более ранняя дата выдачи. Пороги уровней риска: ≥70 критический, 40–69 высокий,
20–39 средний, <20 контролируемый.

## 7. UX-логика

- Клик по любому KPI → отфильтрованный реестр (таблица §2, колонка drill-down).
- Клик по объекту в B4 → детальная аналитика объекта (тот же экран,
  зафиксированный фильтр `object=…`, адрес `/dash/executive?object=…`).
- Любая красная цифра не может быть «просто числом»: переход обязателен,
  в реестре первым столбцем идёт причина цвета (просрочка/категория А).
- Читаемость без прокрутки: базовый шрифт 14 px (таблицы B6 — 13 px),
  KPI-число 32 px; высота строки таблицы 28 px; B6 — ровно 10 строк.
- Обновление: кнопка «Обновить» + автообновление раз в 15 мин (фоновый
  per-request к build_dashboard_data); в шапке — «данные на {дата, время}».
- Печать/PDF штаба: print-friendly версия `/reports/print` с текущими фильтрами.

  захватка В · монолит · **А** · 12.09 · срок 26.09 · **просрочено 9 дн** ·
  не назначен · субподряд «МонолитГрупп» · «Отклонение оси фундамента Б-3/В
  на 42 мм…» · посл. действие: напоминание 27.09 · [Открыть карточку] · балл 90.

## 9. SQL-поля для построения отчёта

Из текущей схемы: `prescriptions.id, doc_number, doc_date, issue_date,
deadline, actual_fix_date, status, description, object_id, contractor_id,
mgmt_id, category_id, kind_id, issuer_id, responsible_user_id,
requires_review, closed_at, created_at`; `objects.name`, `contractors.name`,
`prescription_categories.name`, `prescription_kinds.name`,
`construction_management.name`, `prescription_inspectors.name`,
`users.full_name`; `prescription_history(change_type, comment, created_at,
changed_by_user_id)`; `prescription_attachments(kind='photo')`;
`prescription_norm_refs(status)`; `notifications(status, event_type)` — для
колонки «последнее действие» и статуса напоминаний.

Новые (миграции 00 §8): `sections.name` (M1–M2), `work_types.name` (M3),
`prescriptions.recurrence_of_id` (M5), `system_config.dash.risk_weights` (M8).

## 10. Критерии приемки (специфичные для 01)

1. Экран целиком виден на 1920×1080 без вертикальной прокрутки; при 1366×768
   допускается одна прокрутка до блока B6.
2. Сумма «просроченные + близкие к сроку + остальные открытые» = K1;
   K2 ⊆ K1; каждый drill-down показывает ровно столько записей, сколько на карточке.
3. Tоп-10 реально сортируется по риск-баллу §6; при изменении весов в M8
   порядок пересчитывается без выката.
4. B3 формирует не более 5 пунктов и не бывает пустым при наличии красных KPI
   (правила §5 проверяются тестами на синтетических данных).
5. Динамика B1 автоматически переключает неделю/месяц при смене периода
   (≤ 3 мес — недели, > — месяцы).
6. Все красные значения детализируемы в 1 клик; в реестре сохранены фильтры
   дашборда и позиция возврата.
7. Данные черновиков (`requires_review=1`) не влияют на KPI при выключенном
   переключателе (00 §2).
