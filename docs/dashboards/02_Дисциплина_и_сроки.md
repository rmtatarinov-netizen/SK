# 02. Исполнительская дисциплина и сроки устранения предписаний

Назначение: контролировать своевременность устранения замечаний строительного
контроля; выявлять просрочки, «зависшие» предписания, нераспределённые задачи
и ответственных с ухудшающейся дисциплиной. Аудитория: руководство
Генподрядчика, руководители строительных участков, инспекторы СК
(`manager`, `inspector`; `contractor_responsible` видит срез своих задач).

Экран отвечает на вопросы:

1. Сколько предписаний просрочено прямо сейчас?
2. Какие должны быть устранены сегодня / ≤3 / ≤7 / ≤14 дней?
3. Какие управления, участки, подрядчики, ответственные системно нарушают сроки?
4. Где замечания дольше всего остаются в работе?
5. Сколько замечаний без срока, ответственного или плана устранения?
6. Улучшается или ухудшается дисциплина vs предыдущий период?

Статусы, определения «в срок/просрочено/средняя просрочка» — по
[00 §3–4](00_Обзор_и_общие_правила.md). Все числа — **пример**.

## 2. KPI-карточки

| # | Карточка | Формула | Drill-down | Цвет |
|---|---|---|---|---|
| D1 | Всего открытых | COUNT(OPEN_STATUSES) | `status=open` | синий |
| D2 | Просроченные | открытые ∧ `deadline < today` | `status=open&overdue=1` | красный при >0 |
| D3 | Без ответственного | открытые ∧ `responsible_user_id IS NULL` | `status=open&responsible=none` | серый (дыра данных) |
| D4 | Без планового срока | открытые ∧ `deadline IS NULL` | `status=open&deadline=none` | серый |
| D5 | Закрыть сегодня | открытые ∧ `deadline = today` | `due=today` | оранжевый |
| D6 | Закрыть ≤ 7 дней | открытые ∧ `today < deadline ≤ today+7` | `due_within=7` | жёлтый |
| D7 | Доля закрытия в срок, % | 00 §4, за период | список нарушивших срок | ≥80 зелёный / 60–79 жёлтый / <60 красный |
| D8 | Средняя просрочка, дн | AVG(`today − deadline`) по D2 | те же, сортировка по просрочке | красный при > 5 дн |
| D9 | Максимальная просрочка, дн | MAX по D2 | карточка лидера просрочки | красный |
| D10 | Средний срок устранения, дн | 00 §4 | устранённые периода | синий + тренд ▲▼ к пред. периоду |

## 3. Визуализации

| Блок | Тип | Описание | Drill-down |
|---|---|---|---|
| F1 | Воронка (funnel) | этапы: выдано (`doc_date` периода) → назначено (есть `responsible_user_id`) → в работе (`in_work`) → ожидает проверки (`fixed_pending_review`) → устранено (`actual_fix_date` заполнен) → закрыто (`closed`). Конверсия %, «застряли» — дельта между этапами | клик по этапу → реестр со статусом этапа |
| F2 | Столбцы по неделям | количество просроченных на срез каждой недели (snapshot считается по `deadline` и дате закрытия — восстановимо из истории; до реализации snapshot-таблицы — расчётная реконструкция) | неделя → список просроченных на тот срез |
| F3 | Линия по месяцам | доля своевременного закрытия, % + целевая горизонтальная линия (например 85% — пример) | месяц → нарушившие срок |
| F4 | Гистограмма возраста | открытые по возрастным корзинам 0–7 / 8–14 / 15–30 / 31–60 / >60 дн (возраст от 00 §4) | корзина → реестр `age_from/age_to` |
| F5 | Тепловая карта | X — статусы (new, under_review, in_work, fixed_pending_review, просрочено), Y — ответственный (top-N + «не назначен»); ячейка = COUNT, фон по интенсивности красного (доля просроченных в ячейке) | ячейка → предписания ответственного в статусе |
| F6 | Таблицы-рейтинги (вкладки) | по управлениям (`mgmt_id`), участкам (M1), подрядчикам, ответственным: открытые, просроченные, доля в срок %, динамика к прошлому периоду (▲/▼). Сортировка по доле просрочек | строка → реестр разреза |
| F7 | Календарь дедлайнов | месяц; в дне — число предписаний с `deadline` в этот день; цвет по правилу §5; дни в прошлом с открытыми — «просрочено» | день → реестр `deadline=дата` |
| F8 | Таблица | топ-15 открытых по возрасту (зависшие): номер, объект, возраст, статус, ответственный, последний комментарий | строка → карточка |
| F9 | Реестр просроченных | колонки §4 | строка → карточка + quick-действия |

## 4. Таблица просроченных — колонки

| Колонка | Источник |
|---|---|
| Номер предписания | `doc_number` + тип (заказчика/внутреннее) |
| Объект | `objects.name` |
| Участок | `sections.name` (M1–M2) |
| Категория | `prescription_categories.name` |
| Вид работ | `work_types.name` (M3) |
| Дата выдачи | `COALESCE(issue_date, doc_date)` |
| Плановый срок | `deadline` |
| Дней просрочки | 00 §4, красный счётчик |
| Ответственный | `users.full_name` / «не назначен» (серый) |
| Подрядчик | `contractors.name` |
| Причина просрочки | `overdue_reason_types` + `overdue_reason_text` (M4); пусто → кнопка «заполнить» |
| Последний комментарий | `prescription_comments` (M7) / `prescription_history.comment` |
| Фотоотчёт | ✓/✗ по `attachments.kind='photo'` |
| Управленческое действие | quick-меню §6; последняя выполненная эскалация из `notifications` |

## 5. Правила расчёта (точные, обязательны)

1. «В срок» — `actual_fix_date <= deadline`; если `actual_fix_date IS NULL` у
   закрытого — `DATE(closed_at) <= deadline`.
2. «Просрочено» — `status ∈ OPEN_STATUSES` ∧ `deadline < today` ∧
   `actual_fix_date IS NULL`.
3. «Средняя просрочка» — среднее по `today − deadline` для открытых
   просроченных; для закрытых с нарушением — `факт_устранения − deadline`.
   Записи без срока в расчёт не входят (и учитываются отдельно в D4).
4. «Средний срок устранения» — AVG(`факт_устранения − дата выдачи`) по
   устранённым за период.
5. «Без ответственного» — открытое ∧ `responsible_user_id IS NULL`.
6. «Без срока» — открытое ∧ `deadline IS NULL`.
7. Дни считаются календарными (без рабочих); выходные не исключаются —
   единый подход для всех блоков.

## 6. Светофор (для календаря, таблиц, карточек)

| Цвет | Условие |
|---|---|
| Красный | просрочено; ИЛИ категория А со сроком сегодня/просрочкой |
| Оранжевый | срок через 1–3 дня |
| Жёлтый | срок через 4–7 дней |
| Зелёный | устранено и подтверждено (`closed`) |
| Серый | нет ответственного, нет срока или нет обязательных данных (`requires_review=1`, категория не задана) |

## 7. Действия прямо из дашборда (quick-меню строки и массовые)

Реализация — 00 §7; специфика экрана:

1. **Назначить ответственного** — из F5-пустых и D3; меняет `responsible_user_id`,
   уведомление `responsible_changed`.
2. **Изменить срок** — модалка с обязательным полем «причина» (M4);
   без причины кнопка неактивна; событие `deadline_changed`.
3. **Направить напоминание в Telegram** — ручная постановка `notifications`
   (event `deadline_approaching`/`deadline_overdue`) получателю из
   `recipient_channels`; статус доставки показывается ✉ в строке.
4. **Запросить отчёт об устранении** — уведомление + ожидание фотоотчёта
   (атрибут «нет фото» из колонки §4).
5. **Назначить повторную проверку** — инспектор: `status → fixed_pending_review`
   или возврат `in_work` (пишется в `prescription_history`,
   событие `returned_to_in_work` для возвратов на доработку).
6. **Открыть карточку предписания**.
7. **Выгрузить перечень просроченных в Excel/PDF** — `/reports/export.xlsx`
   с фильтром текущего экрана (доработка: проброс query-фильтров в экспорт).

## 8. Пример наполнения (пример!)

- D1 открытые 47 · D2 просроченные 12 · D3 без ответственного 8 · D4 без срока 5 ·
  D5 сегодня 3 · D6 ≤7 дн 9 · D7 в срок 74,2% · D8 средняя просрочка 11,3 дн ·
  D9 максимальная 42 дн · D10 средний срок 8,4 дн ▼ (было 9,6).
- Воронка: выдано 118 → назначено 104 (88%) → в работе 89 → ожидает проверки 63
  → устранено 58 → закрыто 51 (конверсия 43%).
- Тепловая карта (фрагмент): Иванов И.И. — просрочено 6/8 (красн.);
  Петров П.П. — 1/9 (зелён.); «не назначен» — 8 без ответа (серый).
- Календарь: 08.10 — 3 дедлайна (оранж.), 05.10 — 2 не закрыты (красн.).

## 9. Требования к данным

Обязательны миграции: M1–M2 (участок), M3 (вид работ), M4 (причина просрочки),
M7 (комментарии) из 00 §8. Без M4 колонка «причина просрочки» — только кнопка
ввода. Для F2 нужна snapshot-таблица `dash_daily_stats(date, overdue_cnt)`
(ночная задача воркера уведомлений уже запускается ежедневно — расширить её) — до её
появления F2 строится реконструкцией и помечается «оценка».

## 10. Критерии приемки (специфичные для 02)

1. D2 = сумма просроченных F5; D5+D6+«после 7 дней» = D1 − D2 − D4 корректно
   сходятся при любом срезе фильтров.
2. Каждая красная ячейка/строка детализируется в 1 клик; изменение срока из
   таблицы невозможно без указания причины (UI-тест).
3. Напоминание из дашборда создаёт запись `notifications` с корректным
   `event_type` и доходит до статуса `sent`/`failed` (показывать ✉-статус).
4. Экспорт просроченных повторяет колонки §4 с теми же фильтрами.
5. Пороги §5–§6 покрыты unit-тестами на границах (deadline = today, = today+1,
   = today+7; `actual_fix_date` = deadline → «в срок»).
