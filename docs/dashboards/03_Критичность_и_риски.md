# 03. Критичность, качество и риск

Назначение: риск-ориентированный контроль предписаний. Руководство в первую
очередь видит замечания категории А, потенциально опасные дефекты, повторные
нарушения и проблемы, способные повлиять на безопасность, качество конструкций,
приёмку работ, сроки строительства, претензии заказчика и финансовые потери.

Аудитория: служба строительного контроля, руководство Генподрядчика
(`manager`, `inspector`, `admin`).

**О категориях.** А/В/С — настраиваемая внутренняя классификация компании
(справочник `prescription_categories`), а не нормативные определения.
Система не утверждает соответствие СП/ГОСТ; интерпретация категорий
закреплена локальным положением Генподрядчика и может быть изменена
без доработки кода. Дефолтная трактовка (пример формулировки для карточек
подсказок): А — критические (безопасность/конструкции/приёмка),
В — значимые, С — локальные и менее критичные.

Все числа — **пример**. Определения и миграции — [00 §3–4, §8](00_Обзор_и_общие_правила.md).

## 2. KPI

| # | Показатель | Формула | Цвет |
|---|---|---|---|
| R1 | Открытые категории А | COUNT(открытые ∧ cat=A) | красный всегда |
| R2 | Просроченные категории А | R1 ∧ `deadline < today` | красный при >0 |
| R3 | Доля А среди открытых, % | R1 / открытые × 100 | >15% красный, 8–15% оранжевый, <8% зелёный (пороги настраиваемые) |
| R4 | Повторные замечания | открытые ∧ `recurrence_of IS NOT NULL` (M5) | оранжевый |
| R5 | Без нормативной ссылки | открытые ∧ NOT EXISTS(`prescription_norm_refs` со `status='confirmed'`) | серый/оранжевый (качество данных) |
| R6 | Ожидают повторной проверки | `status = fixed_pending_review` ∧ ранее возвращались на доработку (`history: fixed_pending_review → in_work` — см. `queries.rework_count`) | оранжевый |
| R7 | Средний срок устранения по А/В/С | 00 §4, группировка по категории | сравнение с целевым по каждой |
| R8 | Доля своевременного закрытия по каждой категории | в срок/устранённые × 100 по А, В, С | ≥80/60–79/<60 |
| R9 | Объекты с критическими замечаниями | COUNT(DISTINCT object_id) WHERE R1 | красный при >0 |

Drill-down: как всегда — клик → реестр с условием строки формулы.

## 3. Визуализации

| Блок | Тип | Детали |
|---|---|---|
| P1 | Stacked bar (гориз.) | по каждой категории А/В/С три сегмента: открыто (красн.), просрочено (тёмно-красн.), закрыто за период (зелён.). Клик по сегменту → реестр |
| P2 | Тепловая карта | X — категории А/В/С, Y — объекты; ячейка: цвет = макс. риск-балл (§4) открытых предписаний ячейки, число = COUNT. Сортировка Y по убыванию суммарного риска → клик → реестр объект×категория |
| P3 | Bubble chart | X — повторяемость (среднее число повторов кластера/темы, M5+M6), Y — критичность (средний балл категории), размер — число открытых, цвет — срок/просрочка (§6 палитра 00). Точки — объекты или виды работ (переключатель). Click → реестр |
| P4 | Парето | причины на основе поля `justification` (обоснование), сгруппированные в кластеры M6 (детали кластеризации — [04 §3](04_Виды_работ_и_дефекты.md)); столбцы — частота, линия — накопительная доля %; фокус на 80% массы |
| P5 | Линия/область | по месяцам: выдано А, закрыто А, остаток открытых А (линия остатка — вторая ось). Клик по точке → реестр среза |
| P6 | Матрица | X — категории (А/В/С), Y — виды работ (M3); ячейка = средний риск-балл, фон — градиент красный→серый, число — COUNT |
| P7 | Список | предписания с риск-баллом ≥ 70 (§4), не более 5; формат — [01 §5](01_Панель_руководителя.md) + кнопка «Рекомендуемое действие» (§5) |
| P8 | Реестр | колонки §4, сортировка по баллу |

## 4. Интегральный приоритет (риск-балл)

`Приоритет = вес категории + вес просрочки + вес повторяемости +
вес отсутствия ответственного + вес отсутствия нормативной ссылки +
вес близости срока + вес сложности вида работ`

Пример шкалы (значения хранятся в `system_config.dash.risk_weights`, M8,
и меняются без релиза; согласованы с [01 §6](01_Панель_руководителя.md)):

| Фактор | Условие (поле) | Балл |
|---|---|---|
| Категория А | `category='А'` | 50 |
| Категория В | | 25 |
| Категория С | | 10 |
| Просрочка > 14 дн | открытое, `today−deadline > 14` | 30 |
| Просрочка 1–14 дн | | 20 |
| Дедлайн ≤ 3 дн | `0 ≤ deadline−today ≤ 3` | 15 |
| Повторное замечание | `recurrence_of IS NOT NULL` (M5) | 20 |
| Нет ответственного | `responsible_user_id IS NULL` (открытое) | 15 |
| Нет срока устранения | `deadline IS NULL` (открытое) | 15 |
| Нет нормоссылки при обязательности | нет confirmed `norm_refs`; обязательность — флаг категории/вида работ | 10 |
| Сложность вида работ | справочная таблица `work_types.risk_weight` (0–10): монолит/сварка/АКЗ — выше (пример) | 0–10 |

Интерпретация итогового риска:

| Балл | Уровень | Цвет |
|---|---|---|
| ≥ 70 | критический | красный |
| 40–69 | высокий | оранжевый |
| 20–39 | средний | жёлтый |
| < 20 | контролируемый | зелёный/серый |

Риск-балл считается SQL-запросом (CASE-сумма) для списка/сортировки; при
изменении весов — мгновенный пересчёт на лету (не кэшировать без инвалидации).

## 5. Рекомендуемые действия (блок «автоподсказка» в P7/P8 и карточке)

Генерируются по правилам (не LLM-произвол), с привязкой к кнопкам 00 §7:

| Условие | Рекомендуемое действие |
|---|---|
| А + просрочка > 14 дн | эскалация руководителю проекта (уведомление + фиксация решения в history) |
| А ожидает проверки, ранее возвращалось | внеплановая повторная проверка с выездом |
| Повторное замечание после закрытия | приостановка приёмки соответствующего вида работ на участке |
| Нет нормоссылки при обязательности | запрос плана корректирующих мероприятий у подрядчика |
| Повторяющаяся тема (кластер M6) на ≥ 3 объектах | проверка аналогичных участков |
| Просрочка > 7 дн у подрядчика | вызов подрядчика на техническое совещание |
| Любая карточка P7 | отправка уведомления через Telegram/MAX |
| При закрытии А | прикрепление фото (`attachments kind=photo`) и акта повторной проверки (`kind=act`) — иначе статус не ставится |

## 6. Помощь LLM (все предложения — только черновики до подтверждения инспектором)

Существующая подсистема: `llm/extract_fields.py`, `llm/extract_norm_refs.py`,
RAG (`rag/search.py`, ChromaDB, `norm_docs/norm_chunks/norm_chunk_embeddings`),
логирование вызовов `llm_rag_logs`, статусы `NormRefStatus.SUGGESTED/CONFIRMED`.

| Возможность | Как | Где видно |
|---|---|---|
| Группировка похожих формулировок замечаний | эмбеддинги `description`+`justification`, кластер M6 | P4, 04 §3 |
| Выделение вероятной темы замечания | LLM-классификатор по справочнику видов работ/причин | карточка: чип «тема (не подтверждено)» |
| Поиск похожих ранее выданных предписаний | векторный поиск по closed-массиву + метаданным (объект, участок) | карточка: блок «похожие», кнопка «это повторное» → M5 |
| Предложение нормативных ссылок из внутренней RAG-базы | уже реализовано (`extract_norm_refs`, `rag/recommend.py`) | карточка: suggested → инспектор подтверждает |
| Краткая управленческая сводка | LLM-саммари для колонок «краткое содержание» (01 §4) и еженедельной сводки штаба | 01 B6, экспорт PDF |
| Обязательное ограничение | ни одно LLM-предложение не меняет статус/поле без `confirmed_by_user_id`; `requires_review=1` пока не подтверждено; всё логируется в `llm_rag_logs` | везде — метка «предложено LLM» |

## 7. Пример наполнения (пример!)

- R1 открытых А: **6** · R2 просроченных А: **3** · R3 доля А: 12,8% ·
  R4 повторных: **4** · R5 без нормоссылки: **9** · R6 ждут повторной проверки:
  2 · R7 средний срок: А 11,2 дн / В 7,5 / С 4,1 · R8 в срок: А 58% / В 79% /
  С 91% · R9 объектов с А: **2**.
- Bubble: «монолитные работы» — точка в правом верхнем квадранте (повторяемость
  2,3, критичность 44, размер 14 открытых, цвет красный).
- Парето: топ-причина «отсутствие исполнительных схем» — 24% замечаний,
  первые 4 кластера — 68%.

## 8. Требования к качеству данных

1. Категория обязательна для подтверждения предписания (без `category_id`
   запись не уходит из `requires_review=1` и в KPI не входит, а попадает в
   серый блок «нет данных»).
2. Нормоссылка: проверять наличие хотя бы одной `confirmed`; `suggested` без
   подтверждения более 5 рабочих дней → в R5.
3. Повторность (M5) ставится только инспектором вручную или подтверждённой
   LLM-парой «похожее закрытое предписание»; автоматическая расстановка запрещена.
4. Кластеры причин (M6) принимают управленческий вид (P4) только после
   подтверждения специалистом СК (`confirmed_by_user_id`).

## 9. Критерии приемки (специфичные для 03)

1. Изменение весов в M8 меняет сортировку P7/P8 без кода и перезапуска.
2. Риск-балл каждой строки P8 воспроизводится формулой §4 (SQL-тест на
   границах: 69/70, 39/40, 19/20).
3. Ни одно неподтверждённое LLM-предложение (статус `suggested`) не влияет
   на KPI (тест с `requires_review`).
4. P2 и P6 дают одинаковый суммарный открытый счёт по объект/категория
   (сверка агрегатов).
5. Рекомендуемое действие (§5) появляется для 100% позиций P7 и ведёт к
   исполняемому действию 00 §7.
