# RAG-обоснование предписаний

## Что делает

Для каждого пункта предписания система:

1. Находит в загруженной нормативной базе `top_k` ближайших фрагментов
   (ChromaDB + эмбеддинги `bge-m3` через Ollama).
2. Отдаёт фрагменты локальной LLM (`qwen2.5:7b`) и просит выбрать только
   те, которые действительно обосновывают нарушение, в формате JSON.
3. Проверяет, что выбранный код документа есть в базе: ссылка на норму,
   которой нет в загруженной базе, не сохраняется.
4. Собирает детерминированный текст обоснования из выбранных ссылок,
   причины и дословной выдержки фрагмента.

LLM ничего не подтверждает и не меняет статусы: предложенные ссылки
сохраняются как `suggested` (`norm_refs.status`), подтверждает их инспектор.

## Где хранится

| Поле | Что содержит |
| :--- | :--- |
| `prescriptions.justification` | сводное обоснование по всем пунктам |
| `prescription_items.justification` | обоснование конкретного пункта |
| `prescriptions_norm_refs` | ссылки: `source=rag`, `status=suggested`, `fragment`, `chunk_id` |
| `llm_rag_logs` | промпт, ответ модели, статус и длительность каждого вызова |

Каждое сохранение пишется в историю (`justification:item:<id>`,
`justification`), поэтому изменение обоснования видно в журнале.

## Проверка на тестовом предписании

Тестовое предписание и клиентский PDF создаёт идемпотентный сидер:

```powershell
.\.venv-rag\Scripts\python.exe prescriptions_system\scripts\seed_test_prescription.py --pdf
```

PDF для OCR-цикла: `data/prescriptions/inbox/customer/ТЕСТ-ЗАК-001_2026.pdf`.

Стенд прогонят реальную базу и печатает найденные фрагменты, выбранные
моделью ссылки, совпадение с ожидаемым кодом нормы и текст обоснования:

```powershell
# полный прогон (поиск + LLM), ничего не пишет в БД
.\.venv-rag\Scripts\python.exe prescriptions_system\scripts\check_rag_justification.py

# только векторный поиск, без выбора фрагментов моделью
.\.venv-rag\Scripts\python.exe prescriptions_system\scripts\check_rag_justification.py --no-llm

# сохранить предложенные ссылки и обоснование в БД
.\.venv-rag\Scripts\python.exe prescriptions_system\scripts\check_rag_justification.py --apply

# машиночитаемый отчёт
.\.venv-rag\Scripts\python.exe prescriptions_system\scripts\check_rag_justification.py --report report.json --json
```

Параметры: `--prescription-id`, `--doc-number`, `--top-k` (по умолчанию из
`config.yaml`), `--no-llm`, `--apply`, `--report`, `--json`.

Коды выхода: `0` — проверка выполнена, `1` — ошибка/предписание не найдено,
`2` — Ollama недоступна, `3` — нормативная база пуста.

Итоговая сводка содержит `match_rate` (доля пунктов, где выбранная ссылка
совпала с ожидаемым кодом), `control_clean` (контрольный пункт без
ожидаемой нормы не получил выдуманных ссылок) и `refs_outside_base`.

Ожидаемые коды заданы в `data/testdata/rag_test_prescription.json`.
Ожидания привязаны к именам файлов в `docs/priors/`, поэтому код документа
должен совпадать с именем файла (без расширения).

## Веб-интерфейс

- В карточке предписания у каждого пункта есть поле «Обоснование» и кнопка
  «Подобрать и подставить обоснование (RAG)» — она подбирает нормы по всем
  пунктам, сохраняет ссылки (`suggested`) и заполняет обоснование.
- В реестре колонка «Обоснование» идёт сразу после «Описание нарушений».
- Автоматический подбор не перезаписывает сводное обоснование пустым
  результатом: если модель ничего не выбрала, текст остаётся прежним.

## Обслуживание нормативной базы

Загрузка/перезагрузка документов (код = имя файла):

```powershell
.\.venv-rag\Scripts\python.exe prescriptions_system\scripts\load_norms.py docs\priors\ --pattern "*.pdf"
```

Проверка объёма базы:

```powershell
.\.venv-rag\Scripts\python.exe -c "import sys; sys.path.insert(0, 'prescriptions_system'); from src.rag.search import get_collection; print(get_collection().count())"
```

Если ChromaDB не открывается с ошибкой `Error loading hnsw index` — почти всегда
это известная проблема chromadb 1.0.x на Windows: **движок hnswlib не работает с
каталогами, в чьём пути есть не-ASCII символы** (например, профиль
`C:\Users\Пользователь\...`). SQLite-часть при этом жива, а HNSW-сегменты
молча не записываются: в каталоге остаётся только `index_metadata.pickle` без
`*.bin`, и любое переоткрытие базы падает.

В `src/rag/search.py::ascii_chroma_path` путь автоматически заменяется на
8.3-краткое имя того же каталога (`C:\Users\73B5~1\...`) — оно ASCII и
указывает на те же файлы. Если на томе отключены 8.3-имена, short-путь не
получится: тогда перенесите `rag.persist_directory` в `config.yaml` на путь
только с латинскими буквами.

Проверка признаков: в `data/chroma` есть каталог сегмента, но в нём нет
`data_level0.bin` / `header.bin` — индекс не сохранялся.

Тексты чанков и метаданные при этом не теряются (они в `prescriptions.db`),
поэтому векторы можно пересчитать из сохранённых чанков без повторного
парсинга PDF:

```powershell
# сначала убедитесь, что веб-сервер остановлен, и отодвиньте битый каталог
Move-Item prescriptions_system\data\chroma prescriptions_system\data\chroma.broken
.\.venv-rag\Scripts\python.exe prescriptions_system\scripts\rebuild_chroma.py
```

Скрипт батчами считает эмбеддинги через `/api/embed` (при его отсутствии
переходит на `/api/embeddings`), раскладывает векторы по тем же id
`<document_id>:<chunk_index>` и каждые 1024 записи переоткрывает коллекцию
свежим клиентом — повреждение индекса обнаружится сразу, а не через час.
На CPU без сторонней нагрузки это ~55 минут (bge-m3 идёт по CPU, следите за
`ollama ps`). Флаг `--resume` продолжает прерванную пересборку, пропуская
уже сохранённые id.

## Ограничения

- Без запущенной Ollama не работают ни поиск (нужны эмбеддинги запроса),
  ни генерация — даже с `--no-llm`.
- Имя модели в `config.yaml` (`ollama.llm_model`) должно совпадать с тегом
  установленной модели: `ollama list`. Для Qwen2.5 7B это обычно
  `qwen2.5:7b` (тег `qwen2.5:7b-instruct` есть не во всех сборках).
- Качество зависит от загруженных документов и разбиения на чанки
  (`rag.chunk_size_tokens`, `rag.chunk_overlap_tokens`).
- Обоснование — черновик: окончательное решение и подтверждение ссылок
  остаются за инспектором.
